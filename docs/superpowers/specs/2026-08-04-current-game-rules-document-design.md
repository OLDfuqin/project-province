# 现行游戏规则手册设计

## 目标

建立一份持续更新、面向开发者的现行规则手册，准确记录 Project Province 当前代码中已经生效的玩法规则和数据计算方法。

这份手册用于：

- 在修改规则前快速确认当前行为；
- 统一 C++ 模拟核心、Godot 界面和测试对规则的理解；
- 为数值平衡、缺陷排查和后续系统扩展提供基线；
- 防止尚未实现的设想与当前可玩规则混淆。

## 文档范围

正式规则手册保存为 `docs/current-game-rules.md`。

手册只记录满足以下条件的规则：

1. 已经在当前主分支代码中实现；
2. 能从模拟核心、Godot 桥接层或界面行为中得到验证；
3. 对玩法结果、命令合法性或数据结算有实际影响。

尚未实现的规划、占位按钮和设计设想不写入规则正文。代码没有明确规定的行为标记为“当前未定义”，不根据预期玩法自行补充。

## 目标读者与详细程度

主要读者是开发者。每个系统应尽量记录：

- 数据字段与单位；
- 初始值或固定常量；
- 精确计算公式；
- 结算时机和结算顺序；
- 整数除法、向下取整和上限处理；
- 命令成立的前置条件；
- 命令失败且不改变状态的情况；
- 影响计算结果的科技、地形、道路和外交状态；
- 至少一个能人工复核的计算示例；
- 必要时给出对应代码或测试文件入口。

## 文档结构

规则手册采用单文件结构，初始章节如下：

1. 文档信息与适用版本；
2. 游戏世界与当前剧本；
3. 核心数据类型、数值单位和稳定 ID；
4. 回合、日期与月度结算顺序；
5. 地区控制、法理归属与占领；
6. 总人口和可招募士兵；
7. 地区经济与国家国库；
8. 科技等级、费用与效果；
9. 道路建设；
10. 军队招募；
11. 移动力、寻路与调动；
12. 自动推进计划与策略；
13. 宣战、战争状态和领土通行；
14. 战斗、伤亡、撤退、歼灭与占领；
15. 议和与领土结算；
16. AI 月度决策；
17. 胜利、失败与国家存续；
18. 保存和读取；
19. 当前规则边界与未定义行为；
20. 文档更新记录。

章节顺序优先反映模拟依赖与回合执行流程，而不是界面按钮排列。

## 规则来源与冲突处理

规则以当前 `main` 分支为准，证据优先级为：

1. C++ 模拟核心实际行为；
2. 自动化测试所验证的行为；
3. GDExtension 桥接层公开的数据和命令；
4. Godot 界面展示与交互；
5. 历史设计文档和提交说明。

当界面文字、历史文档与模拟核心不一致时，正文记录模拟核心的实际行为，并单独指出显示或文档差异。不得为了让文字一致而在本任务中修改游戏规则。

## 版本与持续维护

手册顶部记录：

- 游戏核心版本；
- 对应 Git 提交；
- 最后核对日期；
- 文档性质为“当前实现基线”。

以后每完成或修改一项玩法规则，应在同一个功能提交或紧邻提交中同步修改规则手册。更新时必须同时检查公式、结算顺序、边界条件、示例和更新记录。

当单文件已经明显影响检索和维护时，再将各系统拆分到 `docs/rules/`，并保留索引；当前阶段不提前拆分。

## 验证方法

完成规则手册后进行以下检查：

1. 对照所有核心系统头文件和实现文件核对常量与公式；
2. 对照命令处理器核对结算顺序和失败条件；
3. 对照 C++ 与 Godot 自动化测试核对示例；
4. 搜索占位词、模糊表述和规划性内容；
5. 运行 C++ 构建测试和全部 Godot 测试，确认文档工作没有改变游戏行为；
6. 检查 Git 差异，确保只加入文档。

## 非目标

本次不做以下工作：

- 不修改任何玩法公式或数值；
- 不实现尚未完成的功能；
- 不撰写面向普通玩家的简化教程；
- 不把长期路线图混入现行规则；
- 不为了补齐文档而推测未定义规则。
